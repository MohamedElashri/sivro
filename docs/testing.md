# Testing

All fixtures are synthetic. Small ones are committed (`tests/fixtures/excel`,
regenerated with `tests/fixtures/excel/generate.py` and LibreOffice);
everything else is generated by the tests in temporary directories.

## Suites

| Suite | Command | Covers |
|---|---|---|
| Frontend | `make test-frontend` | Mocked Tauri IPC: stale replies, column mapping, exact-number copy, dialogs for CSV/TSV, Excel and SQLite, the JSON document tree, filters and exports |
| Backend | `make test-backend` | Every reader end to end: probing, open, page, filter, sort, count, profile, row expansion and all five exports reopened through the app. Also precision fixtures, malformed and hostile inputs, resource limits, cancellation, refresh, read-only and source-alias guarantees, SQLite WAL and locking, the static DuckDB engine, and repeated open/close |
| Library checks | `make test-libs` | Isolated checks of DuckDB, Calamine and rusqlite behaviour that the readers rely on |
| GUI end to end | `make test-e2e` | The real built app through tauri-driver and WebKitWebDriver: one file per family is opened, exact values are checked, and the app sorts, inspects, counts and closes |
| GUI offline | `make test-e2e-offline` | The same inside a user and network namespace with only loopback, so DNS and external connections fail |
| Performance | `make perf` | 1M-row fixtures per format, measured in fresh optimized processes |

`make ci` runs formatting, clippy and the frontend, backend and library suites.

The GUI tests need a release binary (`make app`),
`tauri-driver` (`cargo install tauri-driver --locked`) and WebKitWebDriver
(Debian/Ubuntu: `webkit2gtk-driver`). They open real windows; use `xvfb-run -a`
on headless machines. On Ubuntu 24.04 the offline run needs
`kernel.apparmor_restrict_unprivileged_userns=0`.

## Performance baseline

The table below was measured on an AMD Ryzen 7 7735H (16 threads) under Linux,
from optimized builds, with each format in a fresh process. Excel is measured
at its 200,000-cell sheet limit. Timings are in milliseconds, and exports
write every row.

| Step | Parquet | CSV | TSV | JSONL | JSON array | SQLite (WAL) | XLSX |
|---|---:|---:|---:|---:|---:|---:|---:|
| Source size (MiB) | 24.4 | 55.5 | 55.5 | 93.6 | 95.5 | 51.5 | 0.6 |
| Rows | 1,000,000 | 1,000,000 | 1,000,000 | 1,000,000 | 1,000,000 | 1,000,000 | 19,999 |
| Open | 14 | 199 | 182 | 5,134 | 5,934 | 1 | 180 |
| First page | 10 | 11 | 9 | 4 | 2 | 0 | 2 |
| Filtered page | 35 | 319 | 286 | 14 | 14 | 0 | 2 |
| Filtered count | 11 | 193 | 187 | 29 | 29 | 15 | 1 |
| Global sort, first page | 640 | 1,141 | 1,099 | 629 | 616 | 0 | 39 |
| Exact count | 0 | 126 | 124 | 0 | 0 | 28 | 0 |
| Page at offset total − 100 | 55 | 560 | 556 | 6 | 2 | 25 | 2 |
| Profile | 40 | 561 | 550 | 33 | 31 | 775 | 5 |
| Export CSV | 654 | 1,657 | 1,709 | 1,102 | 1,087 | 604 | 74 |
| Export Parquet | 338 | 928 | 1,036 | 560 | 522 | 743 | 27 |
| Peak RSS (MiB) | 73.6 | 153.6 | 138.4 | 343.0 | 340.2 | 69.9 | 70.4 |
| Peak scratch (MiB) | 0 | 0 | 0 | 55.8 | 55.8 | 0 | 1.8 |

Notes on the table:
- **Instant counts:** Parquet counts come from metadata, and JSON/JSONL and
  Excel counts are known after staging. SQLite's sort and filter used the
  `INTEGER PRIMARY KEY` index.
- **CSV/TSV** have no index, so filters, counts, deep offsets and sorts
  rescan the file.
- **JSON/JSONL opening** reads every record twice and stages them, at about
  18 MiB/s. The 30 s open budget therefore caps JSONL sources at roughly
  500 MiB.
